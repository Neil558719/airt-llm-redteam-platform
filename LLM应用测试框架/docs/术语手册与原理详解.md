## 二、第一部分：这个框架是干什么的？

### 2.1 一句话定位

> 传统软件测试检验"功能对不对"，AI 测试检验"回答好不好"。

给收银系统写测试：`1 + 1 == 2`，结果确定，有标准答案。
但给一个**陪聊机器人**写测试，问题来了：

- 问它"什么是 RAG？"，它每次都答得不一样，**没有唯一标准答案**；
- 它可能答得很流畅，但**悄悄编造了不存在的"事实"**（这就是幻觉）；
- 它答得对不对，有时连人都要斟酌一下才能判断。

`llmtest` 就是给这类应用当**质检员**的：把"回答好不好"这件事拆成能自动检查的指标，
跑一遍、出一份看得懂的报告。它**基于 pytest**——Python 最流行的测试框架，所以写测试
的方式和写普通单元测试几乎一样。

### 2.2 它具体能测什么（六个能力）

| 能力 | 一句大白话 | 对应函数 / 类 |
|---|---|---|
| 语义断言 | 回答的"意思"对不对（允许换个说法） | `assert_semantic_match` |
| 相似度断言 | 回答和参考文本"像不像" | `assert_similarity` |
| JSON Schema 校验 | 回答是不是符合约定的 JSON 格式 | `assert_valid_json` / `assert_json_schema` |
| LLM-as-Judge | 让一个大模型按评分标准给回答打分 | `assert_llm_judge` / `JudgeSpec` |
| 幻觉检测 | 回答有没有编造上下文里没有的事实 | `assert_hallucination_rate` |
| 质量报告 | 把以上结果汇总成网页看板 | `reports/llm_test_report.html` |

## 三、第二部分：讲原理，用大白话

### 3.1 一次测试是怎么跑的（跟着一个真实用例走）

以 `tests/test_rag_assistant.py` 里的幻觉检测为例，完整流程是：

```
① 提问 ──► ② 被测应用回答（答案 + 检索来源） ──► ③ 拆解成"事实断言" ──► ④ 逐条核对来源 ──► ⑤ 算幻觉率 ──► ⑥ 报告
```

具体代码（`tests/test_rag_assistant.py`，**双模式**：Mock 与真实模型通用）：

```python
_POLICY_CONTEXT = (
    "公司退货政策：签收后 7 天内可无理由退货；"
    "退货需保持商品完好，运费由买家承担。"
)

def test_rag_answer_is_faithful_to_context(app_under_test, llm_client, record_metric):
    # ① 向"被测应用"提问：把资料写进 prompt，要求它只据此作答
    #    （真实模型模式下，这是它"真正看到的那份资料"）
    question = (
        "请只根据以下资料回答问题，不要使用资料之外的信息。\n"
        f"资料：{_POLICY_CONTEXT}\n\n问：退货期限是几天？"
    )
    result = app_under_test.ask(question)
    record_metric("retrieved_chunks", 3, unit="条")

    # ② ③ ④ 框架把回答拆成事实断言，逐条拿"同一份资料"核对
    report = assert_hallucination_rate(result.answer, _POLICY_CONTEXT, client=llm_client, max_rate=0.4)

    # ⑤ ⑥ 幻觉率 = 没被资料支持的断言数 ÷ 总断言数；结果写进报告看板
    assert report.hallucination_rate <= 0.4
```

Mock 模式实际跑出来的结果是：回答"退货期限是签收后 7 天。退货需要保持商品完好。退货需要提前预约。"
拆成 3 条断言，其中"退货期限是签收后 7 天""退货需要保持商品完好"两条资料里有依据（判为 **SUPPORTED**）；
而"退货需要提前预约"这条资料里完全没有（判为 **NOT_SUPPORTED**，即幻觉）。
于是这条用例幻觉率 ≈ 33%，低于阈值 40%，**通过**。

> 一个容易踩的坑：幻觉检测核对用的资料，**必须是被测模型生成时真正看到的那份**（本用例就是写进
> prompt 的 `_POLICY_CONTEXT`），而不是测试方另找的文档。用错了对照物，测出来的就不是"忠实度"了
> （详见 4.4 的"上下文"词条）。

### 3.2 架构：框架由 5 层拼成

```
┌──────────────────────────────────────────────────────────────┐
│  ① 测试层    tests/test_chatbot.py、tests/test_rag_assistant.py │  ← 你写测试
├──────────────────────────────────────────────────────────────┤
│  ② 断言/评测层  semantic / similarity / schema / judge /          │  ← 检查"好不好"
│                 hallucination                                   │
├──────────────────────────────────────────────────────────────┤
│  ③ 客户端层    Mock │ OpenAI 兼容 │ Anthropic（base 抽象）         │  ← 谁来回答 / 谁来当裁判
├──────────────────────────────────────────────────────────────┤
│  ④ 指标层     metrics/tracker.py（每测一条记录一条数据）            │  ← 攒数据
├──────────────────────────────────────────────────────────────┤
│  ⑤ 报告层     reporting/html_report.py（看板）                    │  ← 出报告
└──────────────────────────────────────────────────────────────┘
                ┌── 0️⃣ pytest 插件（plugin.py）把 ①~⑤ 串起来 ──┐
```

- **① 测试层**：写测试的地方。你可以自由地调你自己的应用。
- **② 断言/评测层**：负责"打分"和"判定"。
- **③ 客户端层**：框架统一封装"谁能和模型对话"。可以是**模拟的**（Mock，不用花钱不用联网），
  也可以是**真的**（OpenAI、Anthropic，或者任何 OpenAI 兼容的服务）。
- **④ 指标层**：每跑一条测试，把延迟、幻觉率、分数记进一张"台账"。
- **⑤ 报告层**：测试结束，把台账渲染成网页看板。
- **0️⃣ 插件层**：pytest 在"开始一条测试 / 结束一条测试 / 全部结束"这三个时机，会调用框架的钩子函数，
  分别做"登记 / 记账 / 出报告"。

### 3.3 两种模式：Mock 和真实，为什么都要

| | Mock 模式（模拟） | 真实模式（real） |
|---|---|---|
| 谁在回答 | 框架内置的假模型，按规则返回预设回答 | 真实的 GPT / Claude / DeepSeek… |
| 谁当裁判 | 假裁判，按关键词/文本重合规则打分 | 真模型，读打分细则打分 |
| 需要 API key | ❌ 不需要 | ✅ 需要 |
| 是否联网 | ❌ 不用 | ✅ 要 |
| 结果 | 100% 可复现（确定性） | 每次略有不同 |
| 用途 | 开发调试、CI 冒烟、演示 | 上线前的真实质量评估 |

> **为什么要 Mock？** 因为测试必须**稳定**。真模型回答带随机性，同一断言这次过下次不过，
> 测试就没法用。Mock 保证：同一输入一定得到同一输出，先让框架"跑得通、测得稳"。
> 真实模式留好接口，要测真效果时切过去即可（`LLM_TEST_MODE=real`）。

### 3.4 数据是怎么流进报告的

```
每条测试跑的时候：
   客户端回答耗时 ──────────────┐
   断言分数（语义/相似度/Judge）─┼─► metrics/tracker.py（按"当前用例"记账）─┐
   幻觉率 ─────────────────────┘                                       │
                                                                       ▼
pytest 结束会话 ──► summarize() 汇总（准确率/幻觉率/平均延迟/通过率）──► html_report.py ──► 网页看板
```

`tests/test_rag_assistant.py` 里 `test_rag_answer_latency_recorded` 这条用例什么都没断言，
但它在报告里依然有"延迟"数据——因为**延迟是框架自动采集的**，不用你手动记。

#### 用例 1 · `test_answer_semantically_matches_expected`（语义断言）

```python
def test_answer_semantically_matches_expected(app_under_test, llm_client):
    result = app_under_test.ask("用一句话解释什么是 RAG？")
    assert_semantic_match(result.answer, "检索增强生成，结合检索与生成", client=llm_client, threshold=0.6)
```

**工作原理**
① 调用被测应用：把"用一句话解释什么是 RAG？"发过去（Mock 命中关键词，返回 `"RAG 是检索增强生成，结合了检索与生成。"`）。
② 回答（actual）与期望含义（expected）交给 `assert_semantic_match` → 底层调用 `llm_client.semantic_equivalent`。
③ Mock 裁判怎么判"意思像不像"？算两个数，**取较大者**：向量余弦、期望包含度。
④ 取 0.900 ≥ 阈值 0.6 → **通过**。

**本次运行实际结果**：语义分 0.900（阈值 0.6）→ PASSED。
**为什么这么设计**：回答往往比期望长，光靠余弦会把"意思在、只是说法不同"误判为不像，所以再加"期望包含度"兜底。

#### 用例 2 · `test_answer_similar_to_reference`（相似度断言）

```python
def test_answer_similar_to_reference(app_under_test, llm_client):
    result = app_under_test.ask("介绍一下你自己")
    assert_similarity(result.answer, "AI 助手，解答问题，处理任务", client=llm_client, threshold=0.35)
```

**工作原理**
① 问"介绍一下你自己"，返回 `"我是 AI 助手，可以帮你解答问题、处理任务。"`。
② `assert_similarity` 对回答和参考文本分别 **embed**，各得一个 256 维向量，再算**余弦相似度**。
③ Mock 的 embedding 是"确定性伪向量"：同一句话永远得到同一串数字，共享关键词越多向量越接近。

**本次运行实际结果**：余弦相似度 **0.745** ≥ 0.35 → PASSED。
**注意**：语义断言（用例 1）看"意思是否等价"，相似度断言看"文本有多像"——尺度不同、用途不同。
**真实模式提醒**：向量相似度依赖 Embedding 接口。这是**框架级行为**——评测客户端没有 embedding 模型时，
`assert_similarity` 会**自动跳过**（pytest.skip）而不是失败（Mock 用确定性伪向量仍会测），此时用语义断言替代即可。

#### 用例 4 · `test_json_matches_schema`（Schema 校验）

```python
RAG_JSON_SCHEMA = {
    "type": "object",
    "required": ["name", "category", "features"],
    "properties": {
        "name": {"type": "string"},
        "category": {"type": "string"},
        "features": {"type": "array", "items": {"type": "string"}, "minItems": 2},
    },
    "additionalProperties": False,
}

def test_json_matches_schema(app_under_test):
    result = app_under_test.ask(
        "请只返回一个 JSON 对象，只包含 name、category、features 三个字段"
        "（features 为字符串数组，至少 2 项），不要添加其它字段。"
    )
    data = assert_valid_json(result.answer)
    assert_json_schema(data, RAG_JSON_SCHEMA)
```

**工作原理**
① 先解析 JSON（同用例 3），拿到 `data` 字典。
② `assert_json_schema` 用 jsonschema 校验 `data` 是否符合 `RAG_JSON_SCHEMA`：`name/category/features` 必须有、类型对不对、`features` 是字符串数组、`stars` 在 1~5、**不允许多余字段**。
③ 有不合规就**列出所有违规路径**并抛错（不是只报第一个）。

**本次运行实际结果**：全部字段符合约定 → PASSED。
**为什么重要**：应用要程序化解析模型的 JSON 输出，格式不合约定程序就崩——这层保证"接得住"。

#### 用例 5 · `test_greeting_quality_by_judge`（LLM-as-Judge）

```python
def test_greeting_quality_by_judge(app_under_test, llm_client):
    resp = app_under_test.complete([{"role": "user", "content": "你好"}])
    assert_llm_judge(
        resp,
        JudgeSpec.helpfulness(keywords=("智能助手", "为你服务", "解答问题")),
        min_score=60,
        client=llm_client,
    )
```

**工作原理**
① 问"你好"，拿到问候语回答。
② `assert_llm_judge` 用"有用性细则"（`JudgeSpec.helpfulness`）请裁判打分。**真实模式**：裁判模型读细则文本打分；**Mock 模式**：按细则里的 `keywords` 提示词，看回答命中几个。
③ Mock 判定：命中 3/3 → `score = 1 + 99 × (3/3) = 100.0`。
④ `5.0 ≥ min_score 3` → **通过**。

**本次运行实际结果**：100/100（关键词命中 3/3，缺失 []）→ PASSED；归一化 1.0，贡献给看板"准确率"。
**注意**：`min_score` 是"通过线"；打分结果会归一化后进入"准确率"统计。

#### 用例 8 · `test_rag_answer_is_faithful_to_context`（幻觉检测 · 核心用例）

```python
_POLICY_CONTEXT = "公司退货政策：签收后 7 天内可无理由退货；退货需保持商品完好，运费由买家承担。"

def test_rag_answer_is_faithful_to_context(app_under_test, llm_client, record_metric):
    question = (
        "请只根据以下资料回答问题，不要使用资料之外的信息。\n"
        f"资料：{_POLICY_CONTEXT}\n\n问：退货期限是几天？"
    )
    result = app_under_test.ask(question)                      # 资料写进 prompt，即模型"看到"的资料
    record_metric("retrieved_chunks", 3, unit="条")
    report = assert_hallucination_rate(result.answer, _POLICY_CONTEXT, client=llm_client, max_rate=0.4)
    assert report.hallucination_rate <= 0.4
```

**工作原理**
① 把资料 `_POLICY_CONTEXT` 写进 prompt，要求模型只据此作答——这就是幻觉检测要核对的那份资料。
② `record_metric` 记下"召回了 3 段"——会显示在报告指标里。
③ `assert_hallucination_rate` 把 answer 按标点**拆成 3 条事实断言**，逐条问裁判"这条在资料里有没有依据"。
④ Mock 裁判按 **token 覆盖率**判断（≥50% 支撑 / 含否定词且 35%+ 判矛盾 / 否则无依据）：
   1. "退货期限是签收后 7 天" → 资料里有"签收后 7 天内" → SUPPORTED
   2. "退货需要保持商品完好" → 资料里有"退货需保持商品完好" → SUPPORTED
   3. "退货需要提前预约" → 资料里完全没有"预约" → **NOT_SUPPORTED（幻觉）**
⑤ 幻觉率 = 1 ÷ 3 ≈ **33.3%** ≤ 40% → **通过**。
⑥ 返回的 `report` 还带每条断言的 verdict 与依据，可继续 `assert report.hallucination_rate <= 0.4` 二次确认。

真实模型模式下，模型忠实作答则幻觉率 ≈ 0，同样通过。

### 3.5b 同样的 10 个用例，切到真实模型（模型测模型）：底层原理有何不同

3.5 里那 10 段测试代码，在"模型测模型"模式下**一字不改**——这正是双模式的意义。
切换只发生在命令行（只换"谁被问""谁来评"两个角色），测试逻辑完全复用：

```powershell

```

"模型测模型" = **被测侧也是裸模型**（`--app-*` 那组参数），裁判侧是**另一个**模型（`--llm-*` 那组参数）。
两个模型互相质检：被测模型负责回答问题，裁判模型负责评估答案好坏。

> 常见坑：被测侧也要写 `--app-base-url`（公司网关是 OpenAI 兼容的 newapi），否则框架会按
> `deepseek` 别名自动补官方 `api.deepseek.com` 地址，被测模型就跑到公网去了。

#### 一句话主线：模式只换"人"，不换"题"

- 测试代码 = 3.5 那 10 段，**不动**；
- 切换的只是框架 **③ 客户端层**（见 3.2）：Mock 用规则当裁判，真实模式请 LLM 当裁判；
- 断言 API（`assert_semantic_match` 等）的签名、语义、阈值含义完全一致。

所以两种模式的差别，全部藏在**底层实现**里。下面按"变没变"把 10 个用例分成三类。

#### A 类 · 与 Mock 行为一致（纯规则，不需要任何模型）

| # | 用例 | 说明 |
|---|---|---|
| 3 | `test_returns_valid_json` | `assert_valid_json` 就是 `json.loads` + 兼容 ```json 代码块，纯解析，与模型无关 |
| 4 | `test_json_matches_schema` | `assert_json_schema` 用 jsonschema 库校验，纯规则 |

```json 围栏、多啰嗦几句），恰好更考验解析与断言的稳健性。

#### B 类 · 底层从"规则"换成"真 LLM"（核心差异）

这四条（用例 1、5、8、9）是两种模式差异最大的地方。

**用例 1 · 语义断言**

Mock 裁判是"算术"：把两句话各自转成确定性伪向量，算余弦；回答太长时余弦会被稀释，再加
"期望含义包含度"兜底，取较大者（`llmtest/clients/mock_client.py`）：

```python
def _semantic_equivalent(self, actual, expected, context=None):
    cosine = cosine_similarity(self.embed(actual), self.embed(expected))
    containment = token_containment(expected, actual)  # 期望的关键词被回答覆盖的比例
    score = max(cosine, containment)
    return SemanticResult(equivalent=score >= 0.7, score=score, ...)
```

真实裁判是"读"：把"回答 + 期望含义"拼进一段提示词，让裁判 LLM **读两句话判断语义是否等价**，
输出 `{"equivalent": true/false, "score": 0~1, "reasoning": 理由}`
（`llmtest/clients/openai_client.py`）：

```python
def _semantic_equivalent(self, actual, expected, context=None):
    raw = self._llm_json(prompts.semantic_prompt(actual, expected, context))
    return SemanticResult(equivalent=bool(raw["equivalent"]),
                          score=float(raw["score"]), reasoning=raw["reasoning"])
```

对"换个说法"（换述）的句子，真 LLM 比向量余弦稳健得多；万一裁判返回的 JSON 解析失败，
还会回退到向量余弦兜底。

**用例 5 · LLM-as-Judge**

Mock 裁判靠 `JudgeSpec` 里配置的 `keywords`（关键提示词）数命中率：

```python
def _judge(self, response, spec, context=None, question=None):
    hits = [k for k in spec.keywords if k in response]
    ratio = len(hits) / len(spec.keywords)
    score = round(1.0 + (spec.scale - 1.0) * ratio, 2)   # 3/3 命中 → 满分
```

真实裁判把**评分细则全文**（`spec.criteria`）连同回答发给 LLM，让它按 1~N 打分并给理由：

```python
def _judge(self, response, spec, context=None, question=None):
    raw = self._llm_json(prompts.judge_prompt(response, spec.criteria, spec.scale, context, question))
    score = min(max(float(raw["score"]), 1.0), float(spec.scale))
    return JudgeResult(score=score, reasoning=raw["reasoning"], ...)
```

**关键**：真实模式评判"准确性/相关性"时**必须传 `question`**（原题）。`judge_prompt` 会把原题写进
提示词（`用户问题/输入：…`），裁判才能核对"391"是不是正确答案——不传原题它只能"读着像不像"，
容易给简洁的正确答案打低分（这是真实模式下最容易踩的坑）。

**用例 8 / 9 · 幻觉检测**

Mock 的幻觉检测是"数学"：先把回答按标点**正则分句**（`split_sentences`），再逐条算 **token 覆盖率**
（断言里有多少关键词出现在资料中）：

```python
def _verify_claim(self, claim, context):
    ratio = token_overlap_ratio(claim, context)
    if ratio >= 0.5:                          verdict = SUPPORTED
    elif 含否定词 and ratio >= 0.35:           verdict = CONTRADICTED
    else:                                     verdict = NOT_SUPPORTED
```

真实的幻觉检测是"理解"：**拆断言**和**逐条核对**都交给裁判 LLM——先让 LLM 把回答拆成原子事实，
再逐条发"断言 + 上下文"让它判 SUPPORTED / NOT_SUPPORTED / CONTRADICTED 并摘录证据：

```python
def _extract_claims(self, text):                    # LLM 拆断言
    raw = self._llm_json(prompts.claim_extraction_prompt(text))
    return [str(x).strip() for x in raw if str(x).strip()]

def _verify_claim(self, claim, context):            # LLM 逐条核对
    raw = self._llm_json(prompts.claim_verify_prompt(claim, context))
    verdict = str(raw.get("verdict", "NOT_SUPPORTED")).upper()
    return ClaimVerdict(claim=claim, verdict=verdict, evidence=raw.get("evidence", ""))
```

Mock 靠"字面重叠"近似判断（重叠够多就当有依据）；真实模式靠"读懂语义"判断——"签收后 7 天内"
和"7 天无理由退货"字面重叠有限，但 LLM 能看出它们说的是同一件事，幻觉判定更准。

#### C 类 · 框架级自适应（用例 2 相似度）

Mock 用确定性伪向量（`deterministic_embedding`，同一句话永远得到同一串数字），**永远能算**。

真实模式调网关的 **Embedding 接口**（默认 `text-embedding-3-small`）。如果网关**只开了聊天模型、
没开 embedding**（很多企业网关就是这样），框架会在首次探测时发现不可用，然后**自动跳过**这条
断言（pytest.skip），而不是让用例失败——这是框架级能力，不是这条测试特有的：

```python
# llmtest/assertions/similarity.py
if not client.embedding_available():
    raise EmbeddingUnavailableError(...)      # similarity() 测量函数抛错
...
except EmbeddingUnavailableError as exc:
    pytest.skip(str(exc))                      # assert_similarity 自动跳过
```

所以在你们网关上跑这 10 条，预期是 **9 通过 + 1 跳过**（相似度那条），其余全走聊天接口正常通过。

#### ① 幻觉检测用"真实检索到的来源"（生产级核心）

    sources = "\n".join(result.sources)   # Dify 真实检索到的知识片段

**原理**：Dify 对话接口会返回 `retriever_resources`（检索片段），适配器映射成 `AppResponse.sources`。
幻觉检测把回答拆成事实断言，逐条与"机器人真正看到的知识"核对。Dify 的检索带相似度排名、

#### ② 语义期望必须对齐知识库（真实评测最常见的坑）

```python
KB_QUESTIONS = [

```

**原理**：最初把期望写成笼统的"退货期限是签收后 7 天"，但知识库区分"普通商品 7 天 / 质量问题 15 天"，
裁判 LLM 判两句话"含义不完全相同"，分数 0.55 < 0.6 **挂掉**了。这不是框架或 Dify 的问题，
而是**期望口径没跟知识库对齐**——裁判公平地指出"你期望说一律 7 天，人家答得更精确"。反过来这证明
裁判在认真核对语义，不是放水。改把期望写成分情况表述后通过。

def test_dify_robust_to_paraphrased_questions(app_under_test, llm_client):
    result = app_under_test.ask("退货有没有时间限制？")   # 口语化问法，非知识库原文
    assert_semantic_match(result.answer, "普通商品 7 天内可无理由退货，质量问题 15 天内可退换",

**原理**：真实用户不会按知识库原文提问。这条测"检索 + 语义理解"能不能扛住自然语言问法。
这正是语义断言（而非关键词断言）的用武之地——不要求字面一致，换说法也能判"答对了"。

#### ④ 知识库外拒答（防编造，客服上线底线）

```python
def test_dify_handles_out_of_knowledge(app_under_test, llm_client):
    result = app_under_test.ask("公司团建经费怎么申请？")  # 知识库没有的主题
    assert_semantic_match(result.answer, "知识库中没有相关信息，无法回答",
                          client=llm_client, threshold=0.5)
```

**原理**：客服最该守的底线是"不知道就如实说不知道"，不能一本正经地编造。问一个知识库没有的
主题，期望回答表达"没有该信息"。阈值放低到 0.5，因为真实措辞多变（"抱歉暂未收录""请咨询人事"
等只要语义上表达"没有"都算对）。
**为什么不用幻觉率判拒答**：幻觉率会把"没有相关信息"这句话本身判成无依据（sources 里确实没有
这句话），反而误报。所以**拒答用语义断言**，幻觉率用于"在已有的资料里是否忠实"——两个工具各管一段。

#### ⑤ 相关性 Judge（和准确性互补）

```python
def test_dify_answer_relevant_by_judge(app_under_test, llm_client):
    question = "退货需要满足什么条件？"
    result = app_under_test.ask(question)
    assert_llm_judge(result.answer, JudgeSpec.relevance(), question=question,
                     context="\n".join(result.sources), min_score=60, client=llm_client)
```

**原理**：`JudgeSpec` 提供多套细则——`accuracy` 判"答得对不对"，`relevance` 判"有没有答非所问"，
两个维度互补。都传 `question` 让裁判看到原题，才能核对相关性。**裁判还会收到 Dify 检索到的
`sources` 作为 `context`**——它会拼进打分提示词，让裁判核对"回答是否有知识库依据、是否符合知识库
口径"，而不只是凭自身常识判断。这也让 `JudgeSpec.faithfulness()`（忠实度）等"需对照资料"的维度有意义。

#### ⑥ 多轮会话（上下文承接）

```python
def test_dify_conversation_follow_up(app_under_test, llm_client):
    first = app_under_test.ask("退货期限是几天？")
    follow = app_under_test.ask("那运费谁出呢？",
                                conversation_id=app_under_test.last_conversation_id)
    assert_semantic_match(follow.answer, "退货运费：非质量问题由买家承担，质量问题由商家承担",
                          client=llm_client, threshold=0.6)
```

**原理**：Dify 用 `conversation_id` 维持会话。适配器 `ask()` 支持传会话 id，并在每次调用后把
新一轮 id 存进 `last_conversation_id`。测试先问退货期限，再带会话 id 追问"那运费呢"——机器人要能
记得上文是"退货"话题，答出运费规则而非答非所问。这验证客服的**多轮上下文能力**（真实客服必备）。

#### 与 Mock / 模型测模型的三个对比点

| 维度 | Mock / tests | 模型测模型 | Dify 客服 |
|---|---|---|---|
| 被测形态 | 预设回答（mock-cs） | 裸模型，无 sources | **真实 RAG 机器人**，有真实 sources |
| 幻觉核对对象 | 写进 prompt 的资料 | 写进 prompt 的资料 | **机器人真实检索到的片段** |
| 判定强度 | 规则（token 覆盖） | 真实裁判 LLM | 真实裁判 LLM（更准、也更有随机性） |

一句话：`tests/` 证明框架"能测"，Dify 这 9 条证明框架"能测真实生产系统"——从预设回答一路
升级到真实知识库检索、拒答、多轮对话，覆盖企业客服最关心的质量维度。

### 3.5d Dify 进阶：批量回归 · 历史报告对比 · 双裁判模型对比

在 9 条单点用例之外，把 Dify 项目往"工程化回归"再推一步的三件套：
**批量问题集回归**（一次测一篮子问题）、**历史报告对比**（跨版本看趋势）、
**双裁判模型对比**（体检裁判本身可不可信）。

#### ① 批量问题集回归

数据文件 `examples/dify_bot/question_bank.py` 定义一篮子常见问题（问题 → 期望语义）：

```python
QUESTION_BANK = [
    ("退货期限是几天？", "普通商品 7 天内可无理由退货，质量问题商品 15 天内可退换"),
    ("退货需要满足什么条件？", "商品保持完好、配件齐全、未经损坏，且在退货期限内"),
    # ... 共 7 个，覆盖政策核心 + 口语变体
]
```

用例 `test_dify_question_bank_regression`（第 10 条）循环这一篮子，统计通过率并断言 ≥ 80%：

```python
failures = []
for question, expected in QUESTION_BANK:
    result = app_under_test.ask(question)
    r = semantic_match(result.answer, expected, client=llm_client, threshold=0.6)
    if not r.equivalent:
        failures.append(f"{question} → 分 {r.score:.2f}，理由：{r.reasoning}")
rate = (len(QUESTION_BANK) - len(failures)) / len(QUESTION_BANK)
assert rate >= 0.8, f"问题集通过率 {rate:.0%} 低于 80%：\n" + "\n".join(failures)
```

**原理**：单点断言只能回答"这一个问题过没过"；批量回归回答"整体答对了几成"。它用 `semantic_match`
（测量函数，不抛异常）逐条算分、攒失败列表，最后一次性断言整体通过率——个别问题措辞波动不会让
整条挂掉，失败时还把每个问题、分数、裁判理由逐条列出，方便定位"是哪一类问题没答好"。

#### ② 历史报告对比

每次运行结束，框架把本次摘要写进 `reports/history.json`（时间 / 通过率 / 准确率 / 幻觉率 /
平均延迟 / 被测·裁判），并在最新报告里渲染 **「历史运行对比」表**（最新在上、向下越旧）：

| 时间 | 通过 | 通过率 | 准确率 | 幻觉率 | 平均延迟 | 被测 · 裁判 |
|---|---|---|---|---|---|---|
| 2026-08-12 09:54 | 9 ✓ / 10 | 90% | 85% | 3% | 1200ms | 被测: Dify 机器人 · 裁判: gpt-5.6-sol |

**原理**：`write_report_with_history` 在写报告前把本次摘要追加进 history.json（最多保留 20 条），
再内联成 HTML 表（自包含、离线可看）。这是"回归对比"的核心：**换模型、改知识库、改代码后各跑一轮，
一眼看出通过率 / 幻觉率 / 延迟是变好还是变差**——把"这轮改动有没有引入质量回退"变成可量化判断。
历史归档页 `reports/index.html` 仍负责按时间浏览每份完整报告，两者互补。

#### ③ 双裁判模型对比

脚本 `examples/dify_bot/compare_judges.py`：同一批回答（question_bank 那 14 题），用**两个裁判模型**
分别按同一细则打分，输出一致性：

```
裁判 A = gpt-5.6-sol  |  裁判 B = deepseek-v4-flash  |  通过线 = 60
"退货期限是几天？"
  A: 100/100   B: 95/100   差 5.0  [一致]
...
===== 双裁判一致性汇总 =====
平均绝对分差: 4.0   （0 = 完全同分）
皮尔逊相关:   0.98   （越接近 1，两裁判排序越一致）
通过判定一致率: 100%  （对同一回答判过/不过的吻合度）
```

**原理**：裁判是"评分员"，它本身也要体检——两个裁判对同一批回答打分，若分差大、相关低、
通过判定不一致率高，说明**打分细则有歧义**或**某个裁判不可靠**。这是企业评估里
"评估者一致性（inter-rater reliability）"的落地：LLM-as-Judge 不是随便信一个，而是用第二个裁判交叉验证。
**打分依据**：每个裁判打分时，框架把 `question`（原题）和 Dify 检索到的 `sources`（知识库片段，
作为 `context`）一起拼进提示词——裁判既能核对"有没有答非所问"，又能核对"回答是否有知识库依据"。
如果回答明明有依据、两裁判却分歧大，才是 rubric 有歧义或裁判不合格的信号。
**裁判配置从哪来**：脚本合并"环境变量 `LLM_*` + 公共参数 + 各裁判独立参数"三级配置，优先级为
裁判独立参数 > 公共参数 > 环境变量。同网关同分组用公共 `--api-key`；**网关按厂商分组、两裁判 key
不同时，用 `--judge-?-key` 各传各的**：

```powershell
python examples/dify_bot/compare_judges.py --mode real --provider openai --base-url https://newapi.gosuncn.com/v1 --judge-a gpt-5.6-sol --judge-a-key sk-openai分组 --judge-b deepseek-v4-flash --judge-b-key sk-deepseek分组
```

**没配 `real` 时自动降级 Mock**——脚本能跑但不调真实模型，分数是规则算的，并打印醒目警告。
**产出**：跑完自动生成自包含对比报告 `reports/judge_compare.html`（逐题两裁判分数 + 一致性汇总
卡片），每题可展开查看 Dify 回答与两个裁判的打分理由；带**时间戳归档**与**历史对比记录**（不再只有最近一次）。

#### 三个能力一起看

| 能力 | 回答的问题 | 形态 |
|---|---|---|
| 批量回归 | 整体答对了几成？ | pytest 用例（第 10 条） |
| 历史对比 | 这轮改动变好还是变差？ | 报告内置对比表 |
| 双裁判对比 | 打分本身可不可信？ | 独立脚本 |

### 3.6 被测对象 vs 裁判：两个角色必须分开

新读者最常问的一个问题：**"被测对象"和"裁判"是不是两个不同的模型？我要测的是一个具体 App（比如客服 App）怎么办？**

答案分三层：

**① 它们不是"两个模型"，而是"两个不同的东西"，但裁判必须独立于被测。**

| | 被测对象（App under test） | 裁判（llm_client） |
|---|---|---|
| 是什么 | **你做的那个客服 App 本身**（可能含自己的模型 + 业务逻辑 + 知识库，也可能只是个转发服务） | 框架用来评估回答质量的**评分模型** |
| 谁来调用 | 测试代码调它的接口/函数 | 框架的断言函数自动调它 |
| 为什么必须独立 | —— | 裁判不能是"被测自己"，否则等于**自己给自己打分**（自评偏差，分常虚高） |

> 业界经验：裁判选一个**独立、通常更强**的模型（比如被测用 `gpt-4o-mini`，裁判用 `gpt-4o` 或
> `claude-sonnet-5`）。跨供应商更好，偏差更小。

**② 被测是一个具体 App 时，用"适配器"包一层即可。**

框架的断言只认 `answer` / `sources` / `client=`（裁判），不关心答案从哪来。所以把客服 App
的接口包成 `ask(question) -> AppResponse`，所有断言就都能复用：

```python
from llmtest import AppResponse, register_app, track_latency
import requests

class CustomerServiceApp:
    def __init__(self, base_url, api_key):
        self.base_url, self.api_key = base_url, api_key
    def ask(self, question, user_id=None):
        with track_latency():                      # 真实调用耗时自动进看板
            resp = requests.post(f"{self.base_url}/chat",
                                 json={"question": question},
                                 headers={"Authorization": f"Bearer {self.api_key}"})
        data = resp.json()
        return AppResponse(answer=data["reply"], sources=data.get("citations", []))

@register_app("cs")                                # 注册被测对象
def _build_cs():
    return CustomerServiceApp(base_url=os.environ["CS_BASE_URL"], api_key=os.environ["CS_API_KEY"])
```

**③ 被测对象与裁判各自独立配置，各用一条命令切换。**

```bash
pytest --app cs                        # 被测 = 真实客服 App
pytest --app mock-cs                   # 被测 = 另一个已注册的 Mock 应用
pytest --llm-mode real --llm-model gpt-4o --llm-api-key $KEY   # 裁判 = gpt-4o
pytest --app cs --llm-mode real --llm-model gpt-4o             # 两者同时切
```

裁判走框架的 `llm_client` fixture（真实模式 `--llm-model/--llm-provider`，或环境变量
`LLM_MODEL/LLM_PROVIDER/LLM_TEST_MODE`）；被测对象走应用注册表（`--app` 或 `LLM_APP`）。
测试用例本身一行都不用改。

**没有真实 App？直接把模型当被测对象**——被测侧也能从终端切，不用写适配器：

```bash
pytest examples/model_vs_model/ \
    --app-provider deepseek --app-model deepseek-chat --app-api-key $DEEPSEEK_API_KEY \
    --llm-mode real --llm-provider anthropic --llm-model claude-opus-5 --llm-api-key $ANTHROPIC_API_KEY
```

被测模型的参数是 `--app-model/--app-provider/--app-base-url/--app-api-key`（环境变量 `LLM_APP_*`）；
提供商支持别名 `deepseek/qwen/zhipu/moonshot/ollama/local`，框架自动补默认接口地址。
三种"被测来源"优先级：`--app <注册名>` > `--app-model <裸模型>` > 注册默认应用 > Mock。

> 若客服 App 没有检索来源（纯对话、不是 RAG），`sources` 为空，跳过幻觉检测，
> 改用语义 / Judge / 相似度断言即可。

## 四、第三部分：术语表

> 每个术语：**通俗解释**（含类比）→ **在本框架中的体现**（代码/场景）→ **为什么重要**。

### 4.1 测试的基础设施（pytest 相关）

#### 断言（Assertion）
- **通俗解释**：一条"必须为真，否则这题算错"的检查。就像考试判卷时的"这一问必须对"。
- **框架体现**：`assert_semantic_match(...)` 就是一个断言——分数不够就抛 `AssertionError`，
  pytest 看到它就把这条用例记为"失败"。
- **为什么重要**：整个测试的本质就是一堆断言。

#### pytest / 测试用例（Test Case）
- **通俗解释**：pytest 是 Python 的"监考系统"。一个以 `test_` 开头的函数就是一道考题（用例）。
  跑 `pytest` 就是让监考系统把卷子里所有题做一遍，统计对错。
- **框架体现**：`tests/test_chatbot.py` 里每个 `test_*` 函数是一道题；`@pytest.mark.parametrize`
  把同一道题用多组输入各考一遍（参数化）。

#### 夹具（Fixture）
- **通俗解释**：考前准备好的"道具"。比如"每次考试发一张草稿纸"，夹具负责在考前造好、考后回收。
- **框架体现**：`app_under_test`（被测应用）、`llm_client`（裁判/评测客户端）都是 fixture，
  以参数形式注入测试函数，你不用每次自己 new。

#### 插件（Plugin）
- **通俗解释**：往监考系统里塞的"附加规则"。系统每做一个动作，插件能"插一脚"。
- **框架体现**：`llmtest/plugin.py` 注册了 pytest 钩子——开始测试时登记、结束时记账、
  全部跑完时生成报告。这就是框架能和 pytest 无缝融合的关键。

### 4.2 让"AI 回答"变得可测量（向量与文本）

#### Token（词元）
- **通俗解释**：模型读文本的最小单位，类似"字 / 词 / 子词"。中文里一个"词"常由几个 token 组成。
- **框架体现**：框架的 Mock 判定把文本切成 token 来比较（`llmtest/utils.py` 的 `tokenize`）。
- **为什么重要**：一切"相似度""包含度"计算，前提都是先把文本变成可比较的 token 集合。

#### 分词（Tokenization）
- **通俗解释**：把一句话切成一小块一小块。
- **框架体现**：中文用**相邻两字（bigram）**切，英文按单词切。为什么中文用两字？因为单字太碎——
  "幻觉"和"幻象"都含"幻"，会误判成很像；用"幻觉/觉…"这样的两字组更有区分度。

#### Embedding（向量化 / 词向量）
- **通俗解释**：把一句话变成一串数字（向量）。意思越接近的句子，数字串越"靠近"。
  就像给每句话量身高体重，语义相近的人身材也相近。
- **框架体现**：`client.embed("你好")` 返回 256 个数字。真实模式调 API 的 embedding 接口；
  Mock 模式用"确定性伪向量"（同一句话永远得到同一串数字）。
- **为什么重要**：这是"相似度断言"的底层；也是 RAG 里"检索"的底层（见 4.4）。

#### 余弦相似度（Cosine Similarity）
- **通俗解释**：衡量两个向量"方向像不像"的 0~1 分数。1 = 一模一样，0 = 毫无关系。
  类比：两条"意思向量"之间夹角的余弦，夹角越小越接近。
- **框架体现**：`assert_similarity` 先对两句话各自 embedding，再算余弦；分数低于阈值就失败。
- **为什么重要**：不需要标准答案也能量"像不像"，是 AI 测试最常用的相似度手段。

#### 语义等价（Semantic Equivalence）
- **通俗解释**：两句话"表达的意思一样"，哪怕字面不同。"今天天气不错"和"今天天气挺好"就等价。
- **框架体现**：`assert_semantic_match(回答, 期望含义)`。真实模式让模型判断；Mock 模式用
  "向量余弦 + 期望包含度"取较优——回答很长时余弦会被稀释，所以再看期望的含义有没有被完整包含。
- **为什么重要**：LLM 回答没有标准答案，只有"意思对不对"，这是 AI 测试的核心难题。

#### 结构化输出（Structured Output）
- **通俗解释**：让模型按约定格式输出，比如"必须输出 JSON"。方便程序接着处理。
- **框架体现**：示例测试要求应用"返回 JSON"，再用 `assert_valid_json` 解析、`assert_json_schema` 校验结构。

#### JSON Schema（模式校验）
- **通俗解释**：一份"JSON 长什么样的说明书"。校验器检查输出是否长成说明书要求的样子——
  哪些字段必须有、字段是什么类型、值域多大。
- **框架体现**：`assert_json_schema(data, RAG_JSON_SCHEMA)`，出错时把**所有**不合规的路径都列出来。
- **为什么重要**：应用要解析模型的输出，输出格式不合法程序就崩。这层校验保证"能接得住"。

### 4.3 LLM 评测方法（让模型当裁判）

#### LLM-as-Judge（大模型当裁判）
- **通俗解释**：人工打分太慢太贵，干脆再请一个模型当"评委"，按评分标准给被测模型的回答打分。
- **框架体现**：`assert_llm_judge(回答, JudgeSpec.helpfulness(), min_score=60)`。
  还可传 `context`（知识库片段）和 `question`（原题），让裁判对照资料与题意打分，而非仅凭常识。
- **为什么重要**：很多质量维度（有用性、相关性）没有客观公式，只有模型/人"读起来觉得如何"。

#### Rubric（打分细则 / 评分标准）
- **通俗解释**：评委手里的"评分表"。写清楚 1 分什么样、100 分什么样。
- **框架体现**：`JudgeSpec` 提供 `accuracy / relevance / faithfulness / helpfulness` 等预设细则，
  也可自定义。Mock 模式靠细则里的 `keywords`（关键提示词）做确定性打分。

#### 归一化（Normalization）
- **通俗解释**：把不同量纲的分换算到同一把尺子上（0~1），才能加总平均。
- **框架体现**：Judge 分是 1~100，`JudgeResult.normalized` 把 100 分换算成 100%、60 分换算成 60%，
  报告里的"准确率"就是所有归一化分数的平均。

#### 准确率（Accuracy）
- **通俗解释**：在这套框架里，指"裁判打分的平均水平"（归一化后），不是传统意义上的二分对错。
- **框架体现**：看板"准确率 = LLM-as-Judge 平均"。它是"回答整体多靠谱"的综合分。

### 4.4 RAG 与幻觉（框架的重头戏）

#### RAG（检索增强生成）
- **通俗解释**：先"查资料"再"写回答"。模型写作前，先从知识库/资料库里把相关片段（chunk）捞出来，
  让模型参考着写，从而答得更准、更少胡编。
- **框架体现**：`app_under_test.ask()` 返回 `AppResponse(answer, sources)`——`sources`
  就是模拟"查出来的资料"，被测回答要忠实于它。

#### 召回（Retrieval）与向量数据库（Vector Database）
- **通俗解释**：从资料堆里把和问题最相关的内容找出来。向量数据库存的就是"每段资料的向量"，
  靠向量相似度快速找"最像的几段"。
- **框架体现**：`record_metric("retrieved_chunks", 3)` 记录了"召回了 3 段资料"，
  供报告展示（幻觉检测用例里把资料写进 prompt，即模型"看到"的召回结果）。

#### 幻觉（Hallucination）
- **通俗解释**：模型一本正经地**编造**。它不是在撒谎，而是"顺嘴说错了"，把不存在的"事实"说得像真的。
- **框架体现**：`assert_hallucination_rate` 专门抓这个。
- **为什么重要**：幻觉是 LLM 应用上线最大的风险之一——医疗、法律、客服里一句编造的"事实"会出大问题。

#### 事实断言（Claim）与断言分解
- **通俗解释**：把一大段回答拆成一条一条"可单独验证的小主张"。就像把一段演讲拆成一句句"他声称…"。
- **框架体现**：`client.extract_claims(回答)` 按句号/感叹号把回答拆成若干断言，再逐条核对。

#### 幻觉率（Hallucination Rate）
- **通俗解释**：编造的断言占全部断言的比例。0% 最好，越高越危险。
- **框架体现**：`幻觉率 = 幻觉断言数 ÷ 总断言数`。示例里 3 条断言 1 条编造 → 33%，低于 40% 阈值通过。
- **为什么重要**：把"有没有幻觉"从主观感觉变成**可上线的量化指标**，可以设门槛、做回归对比。

#### 事实一致性 / 忠实度（Faithfulness）
- **通俗解释**：回答里的每句话，是不是都能在给定资料里找到出处。忠于资料 = 忠实度高。
- **框架体现**：`JudgeSpec.faithfulness()` 让裁判按此打分；`assert_hallucination_rate` 则直接逐条核对。
  两者是"宏观打分"和"逐句验收"两种粒度。

#### 上下文（Context）
- **通俗解释**：模型回答时"参考的东西"，包括对话历史 + 检索来的资料（RAG 里的 sources）。
- **框架体现**：`assert_hallucination_rate(回答, 上下文)` 的第二个参数就是它，示例里传的是
  `result.sources`。**这个上下文必须是模型真正看到的那份资料**——用错了对照物，
  测的就不是忠实度了。幻觉检测的本质就是"回答 与 上下文 对不对得上"。

### 4.5 工程实践（怎么测得又快又稳）

#### Mock（模拟 / 桩）
- **通俗解释**：造一个"假对象"代替真东西。测试不用联网、不用花钱、结果还能复现。
- **框架体现**：`MockLLMClient` 用预设回答 + 规则判定，让框架开箱即跑。

#### 延迟（Latency）
- **通俗解释**：从提问到拿到回答花了多久。用户体验的核心指标之一。
- **框架体现**：客户端每次调用自动计时（`app_under_test.complete` 耗时记入"平均延迟"），
  Mock 模式还模拟了约 8ms 延迟以便看板演示。

#### 阈值 / 通过线（Threshold）
- **通俗解释**：及格线。分数 ≥ 线就过，< 线就挂。
- **框架体现**：`threshold=0.7`、`min_score=60`、`max_rate=0.4` 都是阈值。怎么定线需要结合业务，通常由
  一段真实数据的分布来标定。

#### 确定性（Determinism）
- **通俗解释**：同样的输入，永远得到同样的输出。这是"测试可复现"的前提。
- **框架体现**：Mock 全部判定基于规则与哈希，无随机性。

#### 质量看板（Dashboard）
- **通俗解释**：把一堆数字变成一眼能看的仪表盘。
- **框架体现**：`reports/llm_test_report.html`，含通过率/准确率/幻觉率/平均延迟四个大数字 + 三张图
  （幻觉率按风险分色、延迟、裁判分）+ 逐用例明细，支持明暗模式。
- **历史归档**：每次运行保留时间戳副本 + `reports/index.html` 历史索引，可按时间对比不同模型/版本的
  质量变化——"这轮换模型是变好还是变差"，让评估可回归。

#### 被测对象（App under test）
- **通俗解释**：真正要被检验的那个应用。它可以带模型，也可以只是个封装好的服务。
- **框架体现**：`app_under_test` fixture。用 `@register_app("名字")` 注册、`--app 名字` 或
  `LLM_APP` 选择；默认用注册的默认应用。
- **为什么重要**：被测对象和裁判（`llm_client`）是两个角色，必须分开、各自独立配置（见 3.6）。

#### 适配器（Adapter）
- **通俗解释**：给你的接口套一层"转换壳"，让它符合框架期望的样子。就像给不同插头的电器配转接头。
- **框架体现**：`examples/customer_service/adapter.py` 把客服 HTTP 接口包成 `ask() -> AppResponse`；
  用 `with track_latency():` 让自定义调用的延迟也能自动进看板。
- **为什么重要**：框架不关心答案从哪来，只认 `answer + sources`。适配器是"接入任何真实 App"的钥匙。

#### 一键切换（--app / LLM_APP）
- **通俗解释**：不碰测试代码，用一条命令换被测对象或裁判。
- **框架体现**：被测对象 `--app NAME`；裁判 `--llm-mode real --llm-model ...`。
- **为什么重要**：同一套用例可以"Mock 快测 + 真实回归"两套环境复用，CI 与联调之间无缝切换。

## 六、一句话总结

**`llmtest` = 一个"给 AI 回答做质检"的流水线：**
问你写的测试 → 被测应用给回答 → 用**语义/相似度/Schema/Judge/幻觉**五把尺子量它
→ 把分数、延迟、幻觉率记进台账 → pytest 结束时渲染成网页看板，
让你能**量化地回答**："这个 AI 应用的准确率多少、有没有幻觉、响应快不快、这轮改动是变好还是变差。"
