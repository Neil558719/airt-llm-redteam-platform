# 统一目标注册与质量安全桥接说明

## 合并边界

合并的是测试平台能力，不是客服应用。Airt 只注册并运行自己的两个 Dify 目标；LLM 应用测试框架中的 Dify/FastGPT 目标继续由其原生 pytest 入口独立管理：

| 目标名 | 来源 | 应用类型 | 测试重点 |
| --- | --- | --- | --- |
| `airt_dify_text` | Airt 当前配置 | Dify Chat | Prompt Injection、越狱、数据外带；同一次调用附带离线质量检查 |
| `airt_dify_chatflow` | Airt 当前 Chatflow | Dify `advanced-chat` | 工具调用、参数边界、间接注入、工具结果外带 |

LLM 框架中的两个独立应用不再作为 Airt 目标注册：

- 另一套 Dify 客服机器人：继续使用 LLM 框架自己的 Dify 质量测试入口；
- FastGPT 客服机器人：继续使用 LLM 框架自己的 FastGPT 质量测试入口。

每个目标使用不同的 Base URL、API Key、应用 ID、知识库和会话状态。不要用一个 `DIFY_API_KEY` 覆盖所有目标。

## PowerShell 环境变量

```powershell
$env:AIRT_DIFY_TEXT_BASE_URL = "http://<airt-dify>/v1"
$env:AIRT_DIFY_TEXT_API_KEY = "<Airt纯文本Dify应用Key>"
$env:AIRT_DIFY_CHATFLOW_BASE_URL = "http://<airt-dify>/v1"
$env:AIRT_DIFY_CHATFLOW_API_KEY = "<Airt Chatflow应用Key>"
```

Airt 的 YAML/CLI 入口继续使用原来的 `config.dify.yaml` 和 `config.dify.agent.yaml`；目标注册表只用于 Airt 的两个目标，不会替换旧配置。

## 评测上下文

`src/airt/evaluation_bridge.py` 中的 `EvaluationContext` 统一保存回答、真实检索片段、Chatflow 工具调用、会话 ID、延迟、Token 用量和原始响应。这样 `llmtest` 的语义、JSON、Judge、RAG 幻觉评测可以消费 Airt 的结果，同时 Airt 原有安全规则和报告仍然保持不变。

## 用例组织建议

- `cases/common`：客服正确性、补充询问、拒答边界、延迟和结构化输出；
- `cases/quality`：语义匹配、RAG 忠实度、幻觉率、JSON Schema；
- `cases/security`：提示词注入、越狱、目标劫持、数据外带；
- `cases/agent`：工具选择、工具参数越界、禁止调用和工具结果污染；
- `cases/dify` / `cases/fastgpt`：只放 provider 特有字段解析和断言。

质量、安全、稳定性三类指标在报告中分栏展示，不把它们压成一个无法解释的总分。
